**Относится к:** схема версии 1.5, миграция `001_init.sql`, 20 таблиц.

Для человека, который вернётся к проекту через месяц, и для ИИ-ассистента, который начнёт новую сессию с нуля и не будет помнить прежних разговоров.

## 0. С чего начать в новой сессии

```bash
cd server
npm run db:reset      # пересобрать базу с нуля и залить тестовые данные
npm run db:verify     # сверить базу с документом схемы
npm run db:describe   # показать все таблицы с полями
```

Зависимостей нет — `npm install` выполнять не нужно.

| Что | Где |
|---|---|
| Формальная схема — все поля, типы, обоснования | `Docs/db-schema.md` |
| Карта экранов прототипа (31 экран) | `Docs/Карта связей прототипа Ноготочки.xlsx` |
| Паспорт продукта, роли, правила записи | `CLAUDE.md` в корне |

| Подключение, миграции, сиды, проверки | `server/src/db/` |
| Переменные окружения | `server/.env.example` |

**Порядок работы со схемой:** сначала правится `Docs/db-schema.md`, затем добавляется новый файл миграции, затем `npm run db:verify` подтверждает, что база и документ сошлись. Команда возвращает код 1 при расхождениях, поэтому её можно ставить в CI.

## 1. Как устроена база и как она связана с логикой проекта

20 таблиц. Разделить их проще всего по тому, какую часть сервиса они обслуживают.

### 1.1. Пять групп таблиц

| Группа | Таблицы | Какую часть сервиса держит |
|---|---|---|
| Люди и доступ | `users`, `sessions`, `password_reset_tokens`, `role_permissions` | Вход, выход, восстановление пароля, разграничение ролей |
| Справочники студии | `masters`, `service_categories`, `services`, `master_services`, `studio_hours`, `studio_closures`, `settings` | Витрина и всё, что администратор ведёт руками |
| Расписание | `master_schedules`, `schedule_exceptions`, `schedule_change_requests` | Когда мастер работает и когда не работает |
| Записи и резервы | `appointments`, `appointment_services`, `slot_holds`, `slot_hold_services` | Ядро сервиса: запись, перенос, отмена |
| Наблюдение | `notifications`, `audit_log` | Что сервис сообщает пользователю и что фиксирует о действиях |

### 1.2. Главное решение: свободного времени в базе нет

**Таблицы готовых слотов не существует, и заводить её нельзя.** Свободное время вычисляется в момент запроса из четырёх источников: график мастера, часы студии, отклонения от графика, уже занятое время.

Почему так:

- Слот в 10:00 «свободен» не сам по себе, а **относительно длительности выбранных услуг**. Для маникюра на 60 минут свободен, для комплекса на 3 часа — уже нет. Признаком в строке это не выражается.
- Освобождение времени становится бесплатным. Отменили запись, истёк резерв, перенесли визит — время само возвращается в свободные при следующем вычислении. Ничего не нужно «возвращать» отдельным действием, а значит нечему и рассинхронизироваться.
- Таблицу слотов пришлось бы генерировать на 90 дней вперёд для каждого мастера и пересобирать при каждой правке графика. Любой сбой генерации — и клиент видит несуществующее время.

Рабочий запрос расчёта лежит в `db-schema.md`, раздел 5.4. Он не просто иллюстрация — он выполняется на живой базе, и им проверялась схема.

### 1.3. Резерв отделён от записи

Клиент выбирает время на шаге 3 мастера записи, а входит в аккаунт только на шаге 4. Записи без клиента быть не может, поэтому выбранное время держится в отдельной таблице `slot_holds` — десять минут, с таймером на экране подтверждения.

Следствие для кода: пока клиент не подтвердил, в `appointments` ничего нет. Поэтому статистика и выручка считаются без оговорки «кроме брошенных черновиков».

Выбранные услуги при этом лежат в `slot_hold_services`, а не в браузере: путь записи не линейный — с шага 4 клиент может уйти восстанавливать пароль и вернуться **по ссылке из письма**, возможно в другом окне.

### 1.4. Что дублируется намеренно

В нескольких местах данные скопированы из справочников, и это не ошибка нормализации.

**Правило: дублировать можно то, что описывает прошлое; нельзя то, что описывает настоящее.**

- `appointment_services.price_kopecks` и `duration_min` — снимок на момент записи. Повышение цены не должно менять сумму прошлых визитов и отчёт за прошлый месяц.
- `sessions.role_at_login`, `audit_log.actor_role` — роль на момент события. Если администратор сменил роль, старая сессия не должна молча получить новые права, а журнал обязан показывать, кем человек был тогда.
- А вот **название** услуги в составе записи не дублируется: переименование — это обычно уточнение формулировки, и старым записям правильнее показывать актуальное название. Оно берётся по `service_id`.

### 1.5. Что не хранится вовсе

- **Суммарная длительность записи** — выражена через `starts_at` / `ends_at`.
- **Сумма чека** — `SUM(price_kopecks)` по составу записи.
- **Выручка и загрузка** — считаются запросами, таблиц агрегатов нет. Администратору разрешено менять статус задним числом, и предподсчитанные итоги пришлось бы синхронизировать при каждой такой правке. Рассинхронизация отчёта — худший вид бага, потому что тихий.

### 1.6. Формат времени

Все моменты времени — `TEXT` в формате `YYYY-MM-DDTHH:MM:SSZ`, **в UTC**. Такая строка сортируется как текст ровно так же, как во времени, поэтому `ORDER BY` и `BETWEEN` работают без единого преобразования.

Исключение: время суток в графике мастера (`HH:MM`) хранится **местное**, потому что «работаю с 10 до 20» — это про местные часы, а не про абсолютный момент. Перевод делается через `settings.utc_offset_minutes`.

## 2. Сложности и как их решили

Здесь только то, на чём реально споткнулись. Почти всё найдено проверкой на живой базе, а не рассуждением.

### 2.1. SQLite не знает названий часовых поясов

```sql
SELECT datetime('2026-10-06T10:00:00', 'Europe/Moscow');  -- NULL
```

SQLite умеет только `'localtime'` — пояс **операционной системы сервера**, который на VPS запросто окажется UTC и тихо сдвинет весь календарь на три часа. Перевести «10:00 местного» в момент UTC внутри запроса было нечем: расчёт свободного времени возвращал пустой список.

**Решение:** настройка `utc_offset_minutes = 180` рядом с `timezone`. Название пояса осталось для человека, число используется в расчётах.

**Ограничение:** фиксированное смещение верно, пока в поясе нет перевода часов. В России его нет с 2014 года. Если сервис запустят там, где часы переводят, одного числа не хватит.

### 2.2. Внешние ключи в SQLite выключены по умолчанию

Это главный риск всей схемы. Забыть `PRAGMA foreign_keys = ON` — значит получить базу, где все 28 внешних ключей написаны, видны в документации и **не работают ни одного дня**. Ошибки при этом не будет: данные просто начнут расходиться.

**Решение:** `PRAGMA` применяется в `connection.js` при каждом открытии соединения, а `npm run db:verify` отдельно проверяет, что поддержка включена.

### 2.3. SQLite не создаёт индексы на колонках внешних ключей

В отличие от большинства СУБД. Без индекса проверка целостности при удалении родителя читает дочернюю таблицу целиком, и точно так же её читает любой запрос «в обратную сторону».

**Решение:** шесть индексов добавлены там, где по связи реально ходят экраны. Остальные девять FK-колонок сознательно оставлены без индекса: `users`, `appointments` и `services` в этом сервисе не удаляются — вместо удаления меняется `is_active` или статус.

### 2.4. Частичный уникальный индекс не годится для внешнего ключа

У `ux_masters_user` стояло условие `WHERE user_id IS NOT NULL`, чтобы разрешить карточки мастеров без привязанного аккаунта. Оказалось, что:

- **условие было лишним** — обычный `UNIQUE` в SQLite и так допускает сколько угодно строк с `NULL`;
- **из-за него индекс не работал** для проверки внешнего ключа: SQLite не может опереться на частичный индекс.

**Решение:** условие снято.

### 2.5. `PRAGMA table_info` скрывает вычисляемые колонки

Первая версия проверки соответствия базы документу показала пять расхождений. Два из них — `users.email_normalized` и `appointments.active_slot` — оказались ложной тревогой: `table_info` не показывает генерируемые колонки вообще.

**Решение:** в `verify.js` используется `PRAGMA table_xinfo`. В коде оставлен комментарий с объяснением, чтобы это не «починили» обратно.

### 2.6. Уникальный индекс не ловит пересечения интервалов

`ux_appointments_master_slot` отсекает только полное совпадение времени начала. Записи 10:00–11:30 и 10:30–11:00 у одного мастера индексом не отсекаются — в SQLite нет типа-интервала и ограничения исключения, как в PostgreSQL.

**Решение:** проверка пересечений обязана быть в коде API внутри одной транзакции — `BEGIN IMMEDIATE`, проверка, вставка, `COMMIT`. Для этого в `connection.js` есть функция `transaction()`, которая берёт блокировку на запись сразу. Индекс остаётся последним рубежом на случай ошибки в коде, а не единственной защитой.

**Это ещё не реализовано** — появится вместе с API записи.

### 2.7. Одна величина хранилась в трёх местах

Длительность записи выражалась полем `duration_min`, разностью `ends_at − starts_at` и суммой по составу услуг. При изменении состава нужно было не забыть пересчитать все три; пропуск любого давал запись, где сумма не сходится с составом. Такое расхождение не ловится ни одним ограничением — база остаётся формально корректной и тихо показывает неправду.

**Решение:** убраны `appointments.duration_min`, `appointments.total_price_kopecks` и `appointment_services.service_name`; `users.email_normalized` стал вычисляемым полем (`GENERATED ALWAYS AS`), так что вписать в него произвольное значение больше нельзя.

### 2.8. Токен резерва хранился открытым

Все секреты сервиса хешируются, а `slot_holds.session_token` лежал в открытом виде. Риск небольшой — токен удерживает слот десять минут и личных данных не открывает, — но это токен на предъявителя: кто им владеет, тот распоряжается резервом.

**Решение:** поле переименовано в `session_token_hash` и хранит хеш. Правило «в базе лежат только хеши секретов» действует без исключений.

### 2.9. Порядок вставки в тестовых данных

Закрытие студии ссылается на администратора, а пользователи вставлялись позже — внешний ключ это поймал. Мелочь, но показательная: **включённые внешние ключи ловят ошибки сразу**, а не через полгода в виде непонятных данных.

### 2.10. Повторный запуск сидов не должен перехешировать пароли

Если обновлять `password_hash` при каждом запуске, соль и хеш меняются, хотя пароль тот же.

**Решение:** `password_hash` не входит в список обновляемых полей в `ON CONFLICT DO UPDATE`. У существующего аккаунта пароль остаётся прежним.

Записи, наоборот, при каждом запуске пересоздаются: они помечены `admin_note = 'seed'`. Будь они идемпотентны по идентификатору, даты со временем уехали бы в прошлое и календарь опять опустел.

## 3. Драйвер SQLite: `node:sqlite`

**Используется встроенный модуль Node.js `node:sqlite`. Внешних зависимостей у проекта нет вообще** — ни одной строки в `dependencies`, папка `node_modules` не создаётся.

```js
import { DatabaseSync } from 'node:sqlite';
```

### Почему он

| Довод | Пояснение |
|---|---|
| Нечего устанавливать и нечего компилировать | На BeGet не нужны ни `node-gyp`, ни компилятор, ни `python`. Деплой — это копирование файлов |
| Нечему протухнуть | Нет зависимостей — нет обновлений безопасности, нет несовместимостей при обновлении Node |
| Синхронный API подходит задаче | SQLite — это файл, а не сервер. Пул соединений к нему не нужен, соединение одно на процесс |
| Достаточно возможностей | Поддерживает всё, что использует схема: генерируемые колонки, частичные индексы, `ON CONFLICT`, `PRAGMA` |

### Что учитывать

Модуль в документации Node помечен как экспериментальный: API может измениться в следующих мажорных версиях. Для учебного проекта с одной студией это приемлемо, и выигрыш в простоте деплоя перевешивает.

**Запасные варианты**, если `node:sqlite` однажды не подойдёт:

- `better-sqlite3` — зрелый, быстрый, API похож. Минус: нативный модуль, требует компиляции при установке.
- `node-sqlite3-wasm` — работает везде без компиляции, но медленнее.

Замена затронет один файл — `server/src/db/connection.js`. Остальной код обращается к базе только через него.

## 4. Версия Node.js и деплой на BeGet

### Требование

| Версия | Состояние `node:sqlite` |
|---|---|
| до 22.5.0 | модуля нет вообще |
| 22.5 – 23.3 | есть, но **только с флагом** `--experimental-sqlite` |
| **с 23.4.0** | **работает без флага — минимум проекта** |
| 24.x LTS | **рекомендуемая для сервера** |

Node 23 — нечётная ветка, она уже снята с поддержки. На сервер ставим **24 LTS**.

### Где требование зафиксировано

| Файл | Значение | Что это даёт на самом деле |
|---|---|---|
| `server/package.json` | `engines.node: ">=23.4.0"` | Объявление минимума. **Само по себе ничего не запрещает** — npm игнорирует это поле по умолчанию |
| `server/.npmrc` | `engine-strict=true` | Превращает объявление в запрет: `npm install` на неподходящей версии падает с понятной ошибкой и не продолжает работу |
| `server/.nvmrc` | `24` | Версия для `nvm use` — рекомендуемая, а не минимальная |
| `server/src/config/runtime.js` | проверка в коде | Последний и главный рубеж: проверяет версию при каждом запуске любой команды |

Три уровня нужны потому, что срабатывают они в разные моменты. `.nvmrc` помогает разработчику до запуска, `engine-strict` ловит при установке, проверка в коде — при работе. Без последней ни один из первых двух не спас бы: зависимостей у проекта нет, и `npm install` на сервере можно вообще не выполнять.

Вот что печатает npm при неподходящей версии, когда `engine-strict` включён:

```
npm error engine Unsupported engine
npm error notsup Required: {"node":">=23.4.0"}
npm error notsup Actual:   {"node":"v20.11.0","npm":"10.2.4"}
```

### Первое, что проверить на BeGet

```bash
node --version
```

Если меньше 23.4.0 — переключить версию в панели управления хостингом или поставить через `nvm`:

```bash
nvm install 24 && nvm use 24
```

### Если версия не подойдёт

Проект не упадёт с непонятной ошибкой. `server/src/config/runtime.js` проверяет версию и объясняет, что делать:

```
Версия Node.js слишком старая.

Текущая версия Node.js: 20.11.0.
Нужна 23.4.0 или новее — в ней встроенный модуль node:sqlite
работает без дополнительных флагов.

Как поставить нужную версию:
  nvm install 24 && nvm use 24
```

Тонкость реализации, которую не надо «упрощать»: драйвер загружается отложенно через `createRequire`, а не обычным `import`. Статический импорт несуществующего встроенного модуля падает **на этапе связывания модулей**, до того как проверка успеет выполниться, и разработчик увидел бы только `ERR_UNKNOWN_BUILTIN_MODULE` без пояснений.

### Порядок развёртывания

```bash
node --version                  # 24.x
cd server
cp .env.example .env            # заполнить SESSION_SECRET и PASSWORD_PEPPER
npm run migrate                 # создать структуру
npm run db:verify               # убедиться, что схема сошлась с документом
```

`npm install` не нужен. `npm run seed` на боевом сервере **не запускается** — скрипт отказывается работать при `NODE_ENV=production`.

### Резервные копии

Файл базы лежит на сервере локально. Это отмечено в паспорте проекта как риск, и схема его не снимает. Нужен отдельный регламент: `VACUUM INTO` по расписанию с выгрузкой копии за пределы сервера. Путь для копий уже предусмотрен — `DATABASE_BACKUP_DIR`. **Регламент пока не настроен.**

## 5. Что нельзя ломать

Короткий список для того, кто продолжит работу.

1. **Не заводить таблицу слотов.** Свободное время вычисляется. См. 1.2.
2. **Не убирать `PRAGMA foreign_keys = ON`** из `connection.js`. См. 2.2.
3. **Не «нормализовать» снимки цен** в `appointment_services` и `slot_hold_services`. См. 1.4.
4. **Не хранить секреты в открытом виде.** Пароли, токены сессий, восстановления и резерва — только хешами.
5. **Не править применённые миграции.** Изменение схемы — новый файл с большим номером, и сначала правка документа.
6. **Не полагаться на уникальный индекс** как на единственную защиту от двойной записи. Нужна проверка пересечений в транзакции. См. 2.6.
7. **Клиент видит только свои записи.** Выборка идёт по идентификатору пользователя из сессии, а не по параметру запроса. Скрытая кнопка защитой не считается.
